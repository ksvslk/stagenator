# Agent Spec — Stagenator

## Overview
**Stagenator** is a fully autonomous (no human in the loop) engagement & retention agent for three
mobile games — **Subliminal Words**, **AI Movie Quiz**, and **Palindrome**. It runs entirely on
Google Cloud: a scheduled decision loop on **Cloud Run** (triggered by **Cloud Scheduler**) reads
**Google Analytics realtime + daily data**, decides what will most increase engagement, retention,
and acquisition right now, and acts:

1. **Ships new levels** — generates content (Runpod for Subliminal Words puzzles; Veo/Gemini
   for AI Movie Quiz; Gemini for Palindrome), submits them via direct Admin SDK writes that
   replicate the admin dashboards' exact write paths, which triggers the games' existing push
   notifications to players.
2. **Mints & distributes promo/offer codes** — Google Play promo codes via Play Console (headless
   Chrome, no API exists) and App Store offer codes via the App Store Connect API — targeted at
   the right users at the right moment (new user arrived, lapsing user detected, streak reward).
   Codes are delivered through **proffer.codes** (the user's existing code-distribution site,
   repo: `~/Projects/takecodes`): the agent maintains a campaign per game, loads minted codes
   into it, and sends FCM pushes with single-use tokened claim links (`proffer.codes/claim/<token>`,
   no sign-in required). Claims run the site's existing atomic tear transaction server-side, so
   inventory (`availableCodes`), analytics funnel (distributed → redeemed), and reports all flow
   through proffer.codes' existing model — and every claim cross-promotes the other games.
3. **Learns day by day** — a nightly reflection run reviews yesterday's actions vs. outcomes
   (did retention/engagement move?) and updates a persistent playbook in Firestore that shapes
   tomorrow's decisions.

Because the games currently have very few users, the starting policy is reactive: **when a new
user appears or a returning user is detected in GA realtime, respond** (fresh level and/or a
code) — then evolve toward learned timing as data accumulates.

**Per-game capability tiers** (the playbook records each game's tier; the Strategist plans
within it — segment actions everywhere from day one, individual targeting lighting up as app
updates ship):
- **Tier 0 — analytics-only (all games, zero app changes):** GA4 → BigQuery export gives
  per-user (pseudonymous) event data — streaks (e.g. 30-days-active), day-N cohorts, churn
  windows as agent queries. Actions: ship levels, topic/segment pushes, segment code drops
  linking to the proffer.codes campaign page. Palindrome extra: its in-app `promos` banner
  collection (`{activated, title, text, picturePath, link}`) is a push-free delivery channel —
  the agent activates a banner linking to the campaign page.
- **Tier 1 — identity-linked (~7 lines per Flutter app, verified against source: `setUserId`,
  `lastSeenAt` merge-write, `claimUrl` tap-handler branch):** joins GA/BigQuery behavior to
  Firebase uid → FCM token → individual tokened claim links, instant Eventarc trigger.
  Subliminal Words (`operation_hermes`) and AI Movie Quiz (`operation_sunrise`) are both
  one small update away (FCM, url_launcher, Auth all already wired). Palindrome
  (`operation-caerus`, native Android) has no FCM/Analytics dependency — stays Tier 0
  (level curation + promos banners); its iOS app is out of scope.

Every observation, decision, action, and outcome is written to a **Firestore decision ledger**,
which powers observability and the demo dashboard.

**Hackathon fit (Taskmaster category, deadline Aug 31, 2026):** ADK (agent framework ✓),
Gemini 3.5 Flash or newer (✓), Google Cloud services: Cloud Run, Cloud Scheduler, Firestore,
Firebase Test Lab, FCM (✓✓✓). "A complete workflow, not just a chatbot" — no chat UI at all.

## Architecture & Sub-Agents
Pattern from `ambient-expense-agent`: **deterministic workflow in code, LLM only where judgment
is needed.** Single Cloud Run service, three scheduled entry points:

- **Instant trigger** (Eventarc on Firestore): new/returning-user doc writes from the games fire
  the Cloud Run agent within seconds — the fast path for "user just showed up, respond now."
- **Pulse run** (Cloud Scheduler, every 5 min): fetch GA realtime (last ~10 min slice of the
  30-min window — 2× overlap, so nothing is missed between polls) → business rules in code
  detect events (new user, returning user, activity spike, code inventory low) → dedupe against
  the ledger (overlap-safe idempotency) → for each genuinely new signal, the **Strategist**
  (Gemini) decides the action within guardrails → actions enqueued as tasks in Firestore →
  **executor pipelines** run them with retries. Ticks with no signals exit without any LLM call
  (≈$0 at current traffic; all three Scheduler jobs fit the free tier).
- **Daily run** (nightly): fetch GA daily aggregates → **Reflector** (Gemini) compares yesterday's
  ledger actions to outcome metrics → updates the **playbook** document (timing rules, per-game
  cadence, what worked) that the Strategist reads on every pulse.
- **Replenish run** (daily): checks `availableCodes` on each game's proffer.codes campaign;
  mints new batches when low (Play Console via headless Chrome; App Store Connect API) and loads
  them into the campaign. proffer.codes campaigns are the **single code inventory** for all three
  games — the games' legacy in-app `promo_code` collections are explicitly out of scope (user
  decision: unknown state in the apps). Player FCM tokens are read from the games' existing
  `fcmTokensAndroid`/`fcmTokensIos` collections for push delivery.

Executor pipelines (plain code + tools, not free-form agent loops):
- **Level pipeline**: generate content (Subliminal Words: Runpod produces the final puzzle
  image, the **agent generates the solution artifact itself** — highlight-SVG per the strict
  words-level format or sketch-PNG, exactly matching what the admin panel's `SvgEditor`/
  `SketchEditor` produce, contract to be extracted from that source; **Veo 3.1 Lite via
  Vertex AI** for AI Movie Quiz 8-sec clips (~$0.40/video — the game's existing format);
  Gemini for Palindrome. Runpod is for Subliminal Words puzzle generation only)
  → validate (schema + Gemini QA pass + solvability check + **duplicate check**: normalized
  palindrome text vs. all existing `user_submitted_levels`; target word/answer vs. existing
  pack levels for Subliminal Words; movie/answer vs. existing levels for AI Movie Quiz —
  duplicates are rejected before submission, ledgered as `rejected:duplicate`) →
  submit via **direct Admin SDK writes replicating the admin dashboards' exact write paths**
  (verified against `~/Projects/firestore/admin-*-dashboard` source):
  - Subliminal Words: Storage `packs/{packId}/levels/{id}/puzzle_{ts}.webp` + thumb +
    `solution_{ts}.svg`, then transaction on `packs/{packId}/levels/{id}` + `totalLevels`
    increments on pack & category.
  - AI Movie Quiz (project `operation-sunrise`): video to Storage, `levels/{n}` doc,
    `counters/levelsCounter` transaction.
  - Palindrome: via `user_submitted_levels` (verified live): a level goes live by having its
    `solutionToCategory` hints filled for all locales (`hint`, `hint_uk`, `hint_fi`, …),
    a correct next `levelId` assigned (pending = `-1337`), and `isFeatured_v3: true`. The agent
    both curates the existing user-submission backlog (validate palindrome → Gemini fills
    multilingual hints → publish) and submits its own generated palindromes through the same
    path.
  → verify live → (stretch) smoke-test on a Firebase Test Lab real device → push notification
  fires via the games' existing mechanism. **No UI automation for level submission** — browser
  automation is reserved for Play Console only (the one surface with no API).
- **Code pipeline**: reserve a code from the game's proffer.codes campaign → create a
  single-use claim token → send FCM push with `proffer.codes/claim/<token>` → user taps, the
  `claimByToken` Cloud Function runs the existing tear transaction server-side (no sign-in;
  `availableCodes` decremented, analytics `distributed`, `claimedBy: "stagenator:<token>"` for
  channel attribution) → claim page shows the code with a platform-detected store redeem button
  (`play.google.com/redeem?code=…` / `apps.apple.com/redeem?ctx=offercodes&…`) and the
  proffer.codes game grid → redemption inferred from purchase events; unclaimed tokens expire
  and their codes return to inventory.

**takecodes changes (in scope, ~1 day):** all claiming stays on the **existing campaigns** and
existing tear flow; login made invisible via **Firebase Anonymous Auth** (enable in take-codes
console; auto `signInAnonymously()` for visitors arriving from agent links). Routes:
`/claim/:token` (individual, single-use — Tier 1) and `/drop/:dropId` (segment drops: one
shared link backed by N reserved codes, first-come-first-served, capped + expiring — Tier 0),
both validated by one small Cloud Function, both reusing the existing tear-off/reveal/
redemption-guide components. Accepted trade-offs: anonymous repeat-claim abuse bounded by drop
caps; per-drop (not per-user) attribution for segment drops.

Fault recovery: every task is a Firestore document with status/attempts/idempotency-key;
crashed runs resume from the queue on the next scheduler tick; 3 failed attempts → dead-letter
status, surfaced on the dashboard; the loop never wedges on one bad task.

## Example Use Cases
- GA realtime shows a first-time user in AI Movie Quiz → Strategist schedules a welcome promo
  code + confirms a fresh level is live → ledger records decision, delivery, and later whether
  the user returned (D1).
- GA shows a user active for the first time in 6 days in Subliminal Words → Strategist ships a
  new Runpod-generated puzzle level (push notification fires) rather than a code, per playbook.
- Nightly Reflector notices codes sent at 09:00 UTC had 0 redemptions but evening pushes drove
  sessions → playbook updated: shift code sends to 17:00–20:00 local.
- Replenish run finds 2 Play promo codes left for Palindrome → drives Play Console in headless
  Chrome, creates a 50-code batch, loads them into Firestore inventory.

## Constraints & Safety Rules
- **Hard caps in code, not prompts**: ≤1 promo/offer code per user per 7 days; ≤20 codes
  distributed per game per day; ≤3 new levels per game per day; ≤1 push-triggering action per
  game per 4 hours.
- Strategist output is a **structured action** validated against these caps before execution;
  anything outside them is rejected and ledgered, never retried blindly.
- Levels go live only after passing validation (schema + solvability + Gemini QA); a failed
  level is dead-lettered, never published.
- Browser automation only touches one whitelisted domain (Play Console); navigation elsewhere
  is blocked.
- All secrets in **Secret Manager**; nothing in prompts or code. The model never sees raw
  credentials.
- `DRY_RUN=true` mode executes the full loop but stubs external side effects (used in eval/CI).

**Alerting & cost guards (human notified, never in the loop):**
- Agent emits `severity=CRITICAL` structured logs on: 3×-dead-lettered task, pipeline failing
  across consecutive runs, Play Console session expired, empty code inventory with replenish
  failing, claim function erroring. A Cloud Monitoring log-based alert policy emails the user;
  a missing-heartbeat alert catches the agent being down entirely.
- GCP billing budget on the account (threshold emails at 50/90/100% of a monthly cap, default
  €25/mo) covering Cloud Run, Vertex/Veo, and everything else in `operation-sunrise`.
- Replenish run checks the Runpod prepaid credit balance via API; below threshold →
  CRITICAL alert ("top up Runpod, ~N generations left"); at zero the Subliminal Words pipeline
  dead-letters gracefully while other games continue.

## Success Criteria
- **E2E level pipeline**: from a simulated GA "new user" event to a live level in Firestore
  (and admin-panel submission verified) in < 10 min, unattended — demonstrated for all 3 games.
- **E2E code pipeline**: simulated lapsing-user event → code selected, delivered, inventory
  decremented, ledger entry complete — for both stores (Play via Chrome, App Store via API).
- **Replenish**: inventory below threshold → new codes minted without human input.
- **Learning**: after a seeded day of ledger data, Reflector produces a playbook update that
  measurably changes the next Strategist decision (eval-checked).
- **Fault recovery**: kill the service mid-pipeline → next scheduled run completes the task
  exactly once (idempotency verified).
- **Eval suite**: ≥8 cases (Strategist decisions on GA fixtures, guardrail violations rejected,
  Reflector updates) pass agreed LLM-as-judge / trajectory bar via `agents-cli eval`.
- **Demo-ready**: Mission Control dashboard (Vite + Firebase Hosting PWA, Firebase Auth locked
  to the owner) with live Firestore listeners: decision ledger, task queue + dead letters,
  playbook diff view (today vs. yesterday), per-campaign code inventory, GA pulse, spend/Runpod
  balance gauges. Reflector writes a **daily brief** (what I did / what happened / what I
  changed / what needs you) delivered as FCM web push to the owner's phone. **CEO channel**: a
  `directives` collection + dashboard input — guidance is folded into the playbook as tagged
  CEO directives, questions answered into the ledger; async and non-blocking, autonomy
  preserved. 4-min video shows Scheduler → Cloud Run logs → level appears → push lands → code
  minted → dashboard narrating it all.
